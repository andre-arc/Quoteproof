# WAL wins concurrent writes, with caveats

For almost every application that writes concurrently to a local SQLite database, **WAL mode is the right choice**, normally with `synchronous=NORMAL`, a nonzero `busy_timeout`, and `BEGIN IMMEDIATE` for any transaction that may write. WAL does not add write parallelism. Both modes allow **exactly one writer at a time** per database file. What WAL removes is reader/writer blocking: readers and the single writer run against separate snapshots and never wait for each other. WAL also makes each commit much cheaper, so the one write lock is held for less time. Measured gains are large. In a 90%-read/10%-write multi-worker benchmark, WAL delivered **4.6–7.5x the throughput of DELETE+FULL**, and p99 latency fell from 10–38 ms to about 0.15–1.5 ms. The trade is a new class of operational problems. You have to manage checkpointing, a WAL file that can grow without bound under constant readers, weaker crash durability at `NORMAL`, and a hard requirement for shared memory on a single host. Rollback-journal mode is still the correct or required choice on network filesystems, across VM boundaries, for multi-file `ATTACH` transactions that must be crash-atomic, for read-only or single-file distribution, and for a few narrower cases. Neither mode delivers true multi-writer concurrency. The efforts that do (`BEGIN CONCURRENT`, `wal2`, `hctree`) still live only on non-mainline branches as of November 2026.

## One writer either way: WAL changes who waits, not how many write

Rollback-journal modes (DELETE, TRUNCATE, PERSIST) share a five-state file lock: UNLOCKED, SHARED, RESERVED, PENDING, EXCLUSIVE. These three modes differ only in how they finalize the journal at commit. Under this protocol, **any number of readers can hold SHARED, but only one connection can hold RESERVED**, and an EXCLUSIVE lock tolerates no other lock of any kind ([SQLite locking](https://www.sqlite.org/lockingv3.html)). A writer can keep building changes in memory while readers continue. Before it touches the database file, at commit or when its cache spills, it must take PENDING, which blocks new readers. Then it waits for existing readers to drain so it can get EXCLUSIVE ([SQLite locking](https://www.sqlite.org/lockingv3.html)). PENDING exists to stop writer starvation, a real problem in SQLite 2. The cost is that every rollback-mode commit briefly turns the database into a single-user resource.

WAL replaces that file-level contention with byte-range locks in the `-shm` wal-index. Every connection holds SHARED on the main file continuously. A single `WAL_WRITE_LOCK` serializes appends to the log, and five `WAL_READ_LOCK(N)` read-marks let readers pin a snapshot ([WAL file format](https://www.sqlite.org/walformat.html)). The documentation is blunt about both sides: **"readers do not block writers and a writer does not block readers,"** but "since there is only one WAL file, there can only be one writer at a time" ([SQLite WAL](https://www.sqlite.org/wal.html)). The contention cost moves rather than vanishing. Long-lived readers no longer stall writers. Instead they stall *checkpoints*, which cannot copy WAL frames past the oldest active reader's snapshot ([WAL file format](https://www.sqlite.org/walformat.html)).

### SQLITE_BUSY comes from transaction shape more than journal mode

The most common surprise in concurrent-write code is an instant `SQLITE_BUSY` even with a generous timeout. It happens because SQLite's default `BEGIN DEFERRED` starts as a reader and upgrades on first write. If another connection has already written, the upgrade can never succeed, so SQLite returns BUSY immediately (in WAL, `SQLITE_BUSY_SNAPSHOT`) and does not invoke the busy handler ([BEGIN TRANSACTION](https://www.sqlite.org/lang_transaction.html); [result codes](https://www.sqlite.org/rescode.html)). The busy handler is also skipped whenever waiting could deadlock ([busy_handler](https://www.sqlite.org/c3ref/busy_handler.html)). The documented remedy is `BEGIN IMMEDIATE`. If it succeeds, **"no subsequent operations on the same database through the next COMMIT will return SQLITE_BUSY"** ([result codes](https://www.sqlite.org/rescode.html)). That moves all lock waiting to the point where `busy_timeout` actually applies. Engineering write-ups give the same advice and add three more points: keep write transactions short, retry the *whole* transaction on residual BUSY (retrying a single statement keeps the stale snapshot), and accept that IMMEDIATE serializes writers by design ([Bert Hubert](https://berthub.eu/articles/posts/a-brief-post-on-sqlite3-database-locked-despite-timeout)). Simon Willison reports that Rails 8 made IMMEDIATE its default transaction type ([Simon Willison](https://simonwillison.net/tags/sqlite-busy)), a sign the pattern has become mainstream. Rollback mode adds one more BUSY source that WAL lacks: a `COMMIT` can fail because readers are still open, and the application must retry it ([BEGIN TRANSACTION](https://www.sqlite.org/lang_transaction.html)).

## WAL+NORMAL is 5–100x faster because it drops the commit fsync

The speed gap comes from I/O mechanics. A rollback commit writes each changed page **twice**: the original goes to the journal, the new version goes to the database. It also needs two journal flushes, a database flush, and a file delete, which is the commit point ([Atomic Commit](https://www.sqlite.org/atomiccommit.html)). WAL writes each page **once**, sequentially, and commits by appending a frame with a commit marker ([SQLite WAL](https://www.sqlite.org/wal.html)). The synchronous setting then decides how much of the remaining cost is paid. In WAL mode, `FULL` fsyncs the WAL on every commit, while `NORMAL` skips that sync entirely and syncs only at checkpoints ([SQLite WAL](https://www.sqlite.org/wal.html)). In rollback mode, `NORMAL` saves only one of the journal flushes ([Atomic Commit](https://www.sqlite.org/atomiccommit.html)). So the synchronous setting moves throughput far more in WAL than in rollback mode.

The available benchmarks fit that model, though none is a rigorous multi-device study.

| Workload | DELETE+FULL | WAL+FULL | WAL+NORMAL | Source |
|---|---|---|---|---|
| 90R/10W, 4 workers (ops/s, p99) | 7,631 / 10.1 ms | 34,883 / 0.18 ms | 37,640 / 0.15 ms | [WordPress PR #483](https://github.com/WordPress/sqlite-database-integration/pull/483) |
| 90R/10W, 16 workers (ops/s, p99) | 7,888 / 38.3 ms | 47,829 / 1.47 ms | 59,372 / 1.44 ms | [WordPress PR #483](https://github.com/WordPress/sqlite-database-integration/pull/483) |
| 10k single-row autocommit inserts (rows/s) | ~279 | ~442 | ~33,135 | [Sesame Disk](https://sesamedisk.com/sqlite-performance-tuning-high-throughput/) (secondary, unverified original) |
| 1M rows in 1,000-row transactions (rows/s) | 317,176 | 319,398 | 393,045 | [sqlite-bench](https://github.com/benbjohnson/sqlite-bench) |

Three lessons follow. First, under concurrency **DELETE+FULL throughput stays flat as workers increase** while WAL scales, because rollback-mode readers and writers lock each other out. Even durable WAL+FULL is 4.6–6.1x faster there ([WordPress PR #483](https://github.com/WordPress/sqlite-database-integration/pull/483)). Second, for tiny autocommit writes almost the whole win comes from dropping the per-commit fsync. WAL+FULL is only about 1.6x faster than DELETE+FULL, while WAL+NORMAL is about two orders of magnitude faster. Third, **batching matters more than the mode**: at 1,000 rows per transaction, DELETE and WAL+FULL land within 1% of each other. The peer-reviewed VLDB 2022 paper by SQLite's authors reaches the same qualitative result. WAL "produces the highest throughput by a wide margin" on TATP, about 10k TPS on a Xeon server with WAL held at durable FULL. With 100 KB blobs, DELETE was "slightly less than half as fast" because it does about twice the writes ([Gaffney, Hipp et al., PVLDB 15](https://par.nsf.gov/servlets/purl/10390276)).

WAL is slower in a few places. For read-mostly workloads the docs concede WAL is **"perhaps 1% or 2% slower,"** and reads degrade as the WAL grows, because each reader must consult it ([SQLite WAL](https://www.sqlite.org/wal.html)). Writes larger than the auto-checkpoint threshold also lose the write-once advantage. In the VLDB blob test, 10 MB writes each triggered an immediate checkpoint, so WAL wrote twice and performed "mostly similar" to DELETE ([PVLDB 15](https://par.nsf.gov/servlets/purl/10390276)). The often-repeated advice to use rollback mode for transactions over 100 MB is obsolete. Since 3.11.0 (2016), **"WAL mode works as efficiently with large transactions as does rollback mode"** ([SQLite WAL](https://www.sqlite.org/wal.html)). What remains true is that a large transaction needs disk headroom for an equally large WAL.

## Durability and checkpointing: WAL trades the last commits for speed, then charges you at checkpoint time

The official durability matrix is the clearest way to compare the modes ([PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)).

| synchronous | Rollback journal | WAL |
|---|---|---|
| EXTRA | ACID | ACID (same as FULL) |
| FULL | Maybe not durable | ACID |
| NORMAL | Maybe not consistent | Maybe not durable |
| OFF | Not consistent | Not consistent |

Two points are often missed. First, **an application crash loses no committed transaction in any mode or setting**. These settings only matter for OS crashes and power loss ([PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)). Second, rollback mode's default `FULL` is not fully durable. Without `EXTRA`'s directory sync after the journal unlink, "a single transaction that commits right before a power loss might get rolled back upon reboot," though the database will not corrupt ([PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)). WAL+NORMAL, the setting SQLite calls "the best balance between performance and safety for most applications running in WAL mode," **never corrupts but can roll back recent commits** after power loss ([PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)). In WAL mode a failed sync can corrupt the database only during a checkpoint. During a commit it costs durability only ([How To Corrupt](https://www.sqlite.org/howtocorrupt.html)). The docs give no bound on how much WAL+NORMAL can lose. From the sync schedule, it is roughly the work since the last checkpoint. Every guarantee in the table also assumes fsync works, and SQLite warns that "most consumer-grade mass storage devices lie about syncing" ([How To Corrupt](https://www.sqlite.org/howtocorrupt.html)). On macOS, real barriers need `PRAGMA fullfsync` ([PRAGMA fullfsync](https://www.sqlite.org/pragma.html#pragma_fullfsync)).

Checkpointing is the price of WAL. By default a **PASSIVE checkpoint runs inline on the commit that pushes the WAL past 1,000 pages (about 4 MB)**, and again when the last connection closes ([SQLite WAL](https://www.sqlite.org/wal.html)). Because the checkpoint syncs both files, "most COMMIT operations [are] very fast but an occasional COMMIT … much slower" ([SQLite WAL](https://www.sqlite.org/wal.html)). Under NORMAL, all fsync cost concentrates there. The documented fix is to disable auto-checkpoint and run checkpoints from a background thread, so the main path "will never block on a sync operation" ([SQLite WAL](https://www.sqlite.org/wal.html)). One small experiment supports it: periodic PASSIVE checkpoints every 500 writes cut maximum write latency from **53.6 ms to 9.3 ms** and p99 from 0.22 to 0.12 ms ([resqlite Experiment 029](https://danreynolds.github.io/resqlite/blog/experiments/029-periodic-passive-checkpointing.html)). Academic work on asynchronous checkpointing reports up to **92.3% lower write tail latency** ([Walack](https://kms.shanghaitech.edu.cn/handle/2MSLDSTB/352575)).

The four checkpoint modes escalate in force. PASSIVE never waits and can stop short. FULL waits for writers and stale readers. RESTART also waits until readers leave the WAL so the log rewinds. TRUNCATE also shrinks the file to zero bytes ([wal_checkpoint_v2](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html)). A stronger checkpoint whose busy handler gives up **silently falls back to PASSIVE and returns SQLITE_BUSY**, so callers must check the result ([wal_checkpoint_v2](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html)).

The real failure mode is checkpoint starvation. If "there is always at least one active reader, then no checkpoints will be able to complete and hence the WAL file will grow without bound" ([SQLite WAL](https://www.sqlite.org/wal.html)). Reads then slow as the WAL grows, and the file is reused rather than shrunk unless `journal_size_limit` or a TRUNCATE checkpoint intervenes ([PRAGMA journal_size_limit](https://www.sqlite.org/pragma.html#pragma_journal_size_limit)). In practice, leaked prepared statements and always-busy reader pools are the usual culprits. The cure is "reader gaps" plus explicit RESTART/TRUNCATE checkpoints ([SQLite WAL](https://www.sqlite.org/wal.html)).

One 2026-specific item belongs on every checklist. A data race in WAL reset, **present from 3.7.0 through 3.51.2**, can corrupt a database when two connections write or checkpoint at the same instant. It is fixed in **3.51.3 (2026-03-13)**, with backports in 3.44.6 and 3.50.7. SQLite rates it rare and "not an emergency," but it is exactly the concurrent-writer scenario this report is about ([SQLite WAL §11](https://www.sqlite.org/wal.html)).

## Rollback journal still wins wherever shared memory or single-file semantics break

WAL's hard constraint is architectural. The wal-index is an mmapped `-shm` file, so **"all processes using a database must be on the same host computer; WAL does not work over a network filesystem"** ([SQLite WAL](https://www.sqlite.org/wal.html)). The same mechanism breaks across VM boundaries even on one physical machine. On the SQLite forum, Linux-host Docker worked, while Docker Desktop on macOS and Windows corrupted databases, because "a VM has its own memory space" ([SQLite Forum](https://sqlite.org/forum/forumpost/292a68c5e4?t=c)). The walbanger stress tool found 100 containers sharing one VM kernel safe overnight, but expects host-plus-container access to fail. It also notes DELETE mode "might not fail" across that boundary ([walbanger](https://tangentsoft.com/sqlite/dir/walbanger?ci=trunk)). A July 2026 report traced three corrupt databases to a macOS-to-OrbStack VirtioFS bind mount ([deva #431](https://github.com/thevibeworks/deva/issues/431)). Rollback mode is not *safe* over a network either, since locks and fsync remain unreliable there. SQLite says rollback mode "mitigates" these problems but calls remote use "at the user's risk," and recommends either a single host process proxying requests or a client/server database ([SQLite Over a Network](https://www.sqlite.org/useovernet.html)).

Several other cases point the same way. **Multi-file `ATTACH` transactions are crash-atomic only in rollback mode**, which uses a super-journal whose deletion is the commit point. In WAL each file is atomic on its own, so a host crash mid-COMMIT can leave some files updated and others not ([ATTACH](https://www.sqlite.org/lang_attach.html); [Atomic Commit](https://www.sqlite.org/atomiccommit.html)). You must be in rollback mode to change `page_size` ([SQLite WAL](https://www.sqlite.org/wal.html)). Read-only media works with WAL since 3.22.0, but only if the side files exist, can be created, or `immutable=1` is used. SQLite still advises converting to DELETE before shipping a read-only image ([SQLite WAL](https://www.sqlite.org/wal.html)). The extra `-wal` and `-shm` files make WAL "less appealing" as an application file format, and copying a database without its `-wal` can lose committed data or corrupt it ([SQLite WAL](https://www.sqlite.org/wal.html); [How To Corrupt](https://www.sqlite.org/howtocorrupt.html)). Platforms with broken mmap, notably QNX, need WAL's no-shared-memory fallback (`locking_mode=EXCLUSIVE`), which reduces the database to a single connection ([How To Corrupt](https://www.sqlite.org/howtocorrupt.html); [SQLite WAL](https://www.sqlite.org/wal.html)). `:memory:` databases cannot use WAL at all ([PRAGMA journal_mode](https://www.sqlite.org/pragma.html#pragma_journal_mode)).

Applications that genuinely need parallel writers should look past both modes, and none of the options is production-ready mainline SQLite. **`BEGIN CONCURRENT`** allows simultaneous write transactions with optimistic page-level conflict detection, but it still serializes COMMIT. It lives on a branch, and conflicts surface as `SQLITE_BUSY_SNAPSHOT` requiring a full rollback ([begin_concurrent.md](https://www.sqlite.org/src/doc/begin-concurrent/doc/begin_concurrent.md)). **`wal2`** fixes unbounded WAL growth with two alternating logs, not writer concurrency, and stock SQLite cannot open its files ([wal2.md](https://www.sqlite.org/src/doc/wal2/doc/wal2.md)). **hctree** is an incomplete prototype with row-level conflict detection ([hctree](https://sqlite.org/hctree)). Turso's Rust rewrite advertises MVCC concurrent writes with up to 4x throughput, but that is a vendor claim about a different engine ([Turso](https://turso.tech/blog/beyond-the-single-writer-limitation-with-tursos-concurrent-writes)).

## Conclusion

Asking "WAL or rollback" mostly means asking whether every process touching the file shares one kernel and one filesystem. If so, choose WAL. Then do the work that actually determines concurrent-write behavior. Run `BEGIN IMMEDIATE` with a busy timeout and whole-transaction retry. Batch writes. Keep read transactions short so checkpoints can finish. Move checkpoints off the hot path if tail latency matters. Pick `FULL` over `NORMAL` only if losing the last few commits on power loss is unacceptable, and run SQLite 3.51.3 or later. If the file crosses a network, a VM boundary or a read-only image, or must stay crash-atomic with attached databases, choose a rollback journal (with `EXTRA` if true durability matters) and accept that readers and writers will take turns.

The deeper insight is that WAL moves contention rather than removing it. Lock waits that rollback mode puts in front of users become checkpoint debt and WAL growth, which surface later and elsewhere. That is usually a far better trade, but it means a WAL deployment needs monitoring (comparing `wal_checkpoint` log and checkpointed frame counts is a cheap starvation signal) that a rollback deployment never did. Workloads that outgrow a single serialized writer even after all of this have outgrown SQLite's mainline design. Their next step is an experimental branch, a different engine, or a client/server database, not a different journal mode.
